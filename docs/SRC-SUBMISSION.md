# SRC 漏洞发现与提交流程

这份指引按常见 SRC 漏洞提交流程组织发现和记录。具体范围、接受类型、严重级、重复判定和奖励以目标 SRC 项目的实际规则为准。没有提供具体平台规则时保留规则缺项，不猜测平台已经接收。源码维护不启动目标测试，也不自动向平台提交。

## 1. 读规则并固定范围

读取实际 SRC 项目的范围、排除项、可接受漏洞类型、测试限制和提交要求。新建 `assessment_mode:src` 靶标，填写非空 scope 和明确 exclude。用提交草稿的 `program`、`policy_reference`、`policy_basis` 记录项目、真实规则引用与收录依据；这些是分析材料，不能证明漏洞或平台接收。

## 2. 发现具体安全缺陷

根据范围内资产、实际响应和应用行为形成具体漏洞假设，说明操作、输入、身份或资源关系与预期安全控制。候选以 claimed/inferred 保存，不能自行声明 observed 或 confirmed。

单独缺少请求/响应安全头、版本或 banner 暴露、TLS/SSL 配置、Cookie 标志、扫描器的最佳实践建议不进入 SRC 漏洞台账。它们可用于分析攻击面；只有相应真实安全机制取得当前可信证明时，才作为该机制的漏洞记录。严重级不是筛选阈值：低危真实安全缺陷可保留，高危标题不能把建议变成漏洞。

## 3. 最小验证与直接证据

只使用本靶标的内置评估和既有前提。先读取实际证据结构，再核对正常/异常/阴性控制、具体输入和实际身份；HTTP 200、401、反射字符串、响应长度或静态源码都不独立证明漏洞。

`redteam_assessment_review verify:true` 对已有完整材料重新核验当前机器证明；确认须逐项绑定靶标、发现、目标、operation/input/category、完整摘要和机器证明范围。实际证明的严重级上限与限制始终保留。取得直接证据后持久停止该漏洞的主动请求，后续仅离线整理材料；改标题、换参数、标 fixed 或切换 preset 不撤销停止。

## 4. 查重与整理提交草稿

先核对本靶标中同目标、同机制、同根因的已有发现及操作者已提供的历史单号。`duplicate_check:checked_local` 只表示本地/已提供资料的查重；`potential_duplicate` 需要进一步复核，不能声称查过平台全库。

每项草稿至少包含：

- 真实 SRC 项目、规则引用、范围和收录依据。
- 具体目标、漏洞类别与当前证明对应的标题。
- `submission.prerequisites`：实际账号角色、资源及必要前提，秘密使用句柄或脱敏标识。
- `reproduction`：最少复现步骤、HTTP 方法、具体输入/操作、对照与已有证据 ID。
- `submission.expected_result`：安全控制应有的结果；实际异常由可信观察和证据引用描述。
- `impact`：已证明影响与待核实影响分开，不把表达式求值扩大为命令执行或主机控制。
- `remediation`：对应根因的修复建议与修复后应有的行为。
- 合法证据引用和必要脱敏附件；不把真实凭据、无关业务数据或原始私有配置写入公开报告。

用 `redteam_vuln_add/update` 保存这些草稿字段，用 `redteam_src_report` 生成 Markdown/JSON。字段完整但未通过当前证明检查的仍是候选；证明成立但字段缺失的显示材料待补。只有两项均满足才显示“提交草稿完整”，同时始终标记平台接收尚未判定、尚未提交。

## 5. 提交、平台复核与修复

操作者依据实际项目表单复核标题、规则、脱敏和附件后提交。插件不会代发消息或自动提交，不伪造平台单号、接收、奖励或最终严重级。平台要求补充材料时先整理已有证据；已停止目标不自动重复请求。

修复结果在原记录中登记 fixed，原证据与停止记录保留。需要主动复测时另建有明确范围与任务授权的独立任务，重新建立当前请求、身份与完整证据；原 SRC 任务不能通过切换渗透/红队撤销停止。

## 状态与剩余工作

`security_candidate` 为待验证安全缺陷，`impact_review_required` 为影响待核实，`report_incomplete` 为已核实但草稿待补，`submission_ready` 为本地提交材料检查通过。`excluded_hardening` 为不进入 SRC 漏洞数的配置/信息项。

来源导入、机器复核与交付页优先复用各自返回的 `next.arguments`；旧 offset 接口继续兼容。报告只整理本地材料，不增加范围、不发送目标请求，也不表示整个范围已耗尽。
