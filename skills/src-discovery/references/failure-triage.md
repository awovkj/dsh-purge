# 失败来源与下一步

先核对请求是否实际派发，以及已有 run/evidence/operation ID。平台 scope、模式或工具拒派发生在请求之前，不能写成“目标 WAF 拦截”或目标安全控制有效。HTTP 401/403/429 则是实际响应状态；仅凭状态不能确定 WAF、业务权限判定或网络隔离。

| 来源 | 可依据的当前事实 | 可执行的下一步 |
| --- | --- | --- |
| 平台/模式拒派 | 明确策略错误码、没有派发回执 | 离线核对固定入口与本任务前提；不换编码、工具名或模式重放 |
| 输入/权限安全机制 | 同操作控制证明请求被校验或拒绝 | 记录该控制的有界结果；它不证明其他输入或身份安全 |
| 目标访问限制 | 真实 HTTP 403/429、登录或网络条件 | 保留条件和未测分母；补实际相关前提前不重复请求 |
| 运行时缺件 | provider、浏览器、解释器或适配器明确不可用 | 只阻塞依赖项，继续独立已具备前提的工作 |
| 请求/连接错误 | 实际 timeout、TLS、解析或连接错误 | 留错误和部分材料，分开判断是否存在未知状态变化 |
| 证据关联错误 | 缺片、旧 lineage、哈希/身份/selector 不匹配 | 离线核对已有材料；不把相似响应或行政修改当成新证据 |

“安全机制”与“外部约束”是解释问题的分类，不是绕过授权，也不是放宽漏洞门槛。外部网关、IP 白名单或未部署组件造成受阻时，不能按“假设绕过后可能取得的数据”定级或提交已确认漏洞。保留 candidate/blocked，并说明实际缺失的验证条件。

同任务失败历史应跨分页和行政处置保留。换时间戳的同请求/响应、重复 baseline、consumer 声明、N/A、checkpoint 与报告都不能重置停滞预算。新材料必须对应实际相关请求/响应、身份核实或安全控制闭环。

未知写入不自动重放。先保存当前 run、partial evidence、effect 状态和 fixture 信息；实际只读读回也须满足当前范围和停止策略。没有可靠读回就保持 effect_unknown，而不是把超时当成“写入失败可重试”。

收束时先整理已有材料、受阻原因、剩余义务及恢复前提。用户取消、新输入、SRC 停止与实际缺失前提优先；持续调用工具不等于产出了安全证明。
