# 身份、对象与授权对照

匿名请求返回 401 只能说明该请求需要认证。它没有测试普通用户之间、租户之间、普通用户与管理员之间的授权关系。先把待核实命题写成“主体 B 是否能在操作 O 读取属于主体 A 的对象 R”，再核对实际服务端主体、角色、租户和对象所有权。

读取已有完整材料，使用 `evidence.read` 找到真实对象字段与 JSON Pointer。对象 ID、URL 或前端角色文字不能代替所有权和身份核实。用实际自我信息端点的 `identity.verify` 验证会话；登录成功、200 和 Cookie 存在仍属于未验证状态。SRC 不提供凭据库，缺必要测试身份时保留相应义务受阻，不借另一个会话的凭据或降级模式。

| 对照 | 要保留的同一条件 | 需要回答的问题 |
| --- | --- | --- |
| 允许主体访问自有对象 | operation、真实对象、请求字段与服务端身份 | 正常访问是否实际返回预期测试对象？ |
| 禁止主体访问同一对象 | 同一对象与 operation，仅改变经过验证的主体 | 是否返回了不应取得的具体内容？ |
| 不存在或不属于该测试的对象 | 相同请求结构、准确资源绑定 | 差异是否只是查找失败、空记录或动态噪声？ |

使用已有自有测试对象和最小样本。业务写测试还需要相应模式允许的变更、可回收 fixture、真实前态和读回；SRC 的业务写入限制继续生效。不要为“补对照”读取其他真实用户的大量记录。

v1 从当前义务执行 `assessment.prepare`，按返回的身份与资源前提组织控制；v2 使用当前 Campaign 的实际配方。自动 provider 缺失就保留缺口，不把静态身份声明或 generic 测试替代授权 oracle。请求、身份 generation、对象、operation/input 和证据完整性必须满足同一原生判据。

离线复核通过后，来源发现仍须匹配当前 native proof 和严重级上限。SRC 直接证据到位即停止该项，后续只整理已有复现；渗透模式可继续其他获准控制，不能把一条越权读取扩写成管理员接管。
